Preventing Cross-Site Request Forgery (CSRF) in a React and Node.js application depends heavily on your authentication
strategy: **Token-Based (JWT in Storage)** or **Cookie-Based Sessions**.

---

### Strategy 1: Cookie-Based Authentication (Most Common & Recommended)

If your Node.js backend uses HTTP-only cookies to store session IDs or JWTs, browsers automatically send these cookies with
cross-site requests. You must actively defend against CSRF using the **Double Submit Cookie Pattern** or **CSRF Tokens**.

#### 1. Set the `SameSite` Cookie Attribute (First Line of Defense)

Configure your cookie middleware in Express (`cookie-session` or `express-session`) to set `SameSite=Lax` or
`SameSite=Strict`.

```javascript
// Node.js (Express)
res.cookie("token", jwtToken, {
  httpOnly: true, // Prevents XSS access to cookie
  secure: process.env.NODE_ENV === "production", // Requires HTTPS
  sameSite: "lax", // Protects against most cross-site POST requests
});
```

#### 2. Implement Double-Submit CSRF Tokens

Because `SameSite` isn't a full replacement for CSRF protection in all edge cases or older browsers, use custom Anti-CSRF
headers.

**Backend (Node.js/Express):**

1. Send a non-`httpOnly` CSRF token in a cookie or a dedicated endpoint.
2. Verify the CSRF header on state-changing routes (`POST`, `PUT`, `DELETE`).

```javascript
const crypto = require("crypto");

// Middleware to generate CSRF token
app.get("/api/csrf-token", (req, res) => {
  const csrfToken = crypto.randomBytes(32).toString("hex");
  // Send token to frontend (in a readable cookie or body)
  res.cookie("XSRF-TOKEN", csrfToken, { sameSite: "lax" });
  res.json({ csrfToken });
});

// Middleware to verify CSRF token on state-changing requests
const verifyCsrf = (req, res, next) => {
  if (["GET", "HEAD", "OPTIONS"].includes(req.method)) {
    return next();
  }
  const tokenFromHeader = req.headers["x-xsrf-token"] || req.headers["x-csrf-token"];
  const tokenFromCookie = req.cookies["XSRF-TOKEN"];

  if (!tokenFromHeader || tokenFromHeader !== tokenFromCookie) {
    return res.status(403).json({ message: "Invalid CSRF Token" });
  }
  next();
};

app.use("/api/", verifyCsrf);
```

**Frontend (React + Axios):** Axios automatically reads the `XSRF-TOKEN` cookie and sets the `X-XSRF-TOKEN` header on
outgoing requests if configured properly.

```javascript
import axios from "axios";

const api = axios.create({
  baseURL: "https://api.yourdomain.com",
  withCredentials: true, // Required to send/receive cookies cross-origin
  xsrfCookieName: "XSRF-TOKEN", // Cookie name sent by Express
  xsrfHeaderName: "X-XSRF-TOKEN", // Header name expected by Express
});

// Example Request
export const updateEmail = async (newEmail) => {
  return await api.post("/api/user/email", { email: newEmail });
};
```

### Strategy 2: Bearer Token Authentication (In-Memory / LocalStorage)

If React stores JWTs in JS memory or `localStorage` and manually includes them via the standard `Authorization` header:

```javascript
// Header sent manually by React:
// Authorization: Bearer <your_jwt_token>
```

**Why this is immune to CSRF:** Browsers **never** automatically attach custom authorization headers to cross-site requests
or standard HTML form submissions from malicious sites.

- **Trade-off:** Storing tokens in `localStorage` makes your app vulnerable to Cross-Site Scripting (XSS). If an attacker
  executes script on your site, they can steal the token.

---

### CSRF Protection Checklist

- **Use CORS properly:** Set strict origin policies on your Node.js server to prevent unauthorized domains from making API
  calls.
- **Avoid `GET` requests for state changes:** Never modify data, log users out, or trigger actions via `GET` endpoints.
- **Require `Custom Headers`:** Even a simple requirement for custom headers like `X-Requested-With: XMLHttpRequest` prevents
  traditional HTML form submission attacks from malicious sites.
