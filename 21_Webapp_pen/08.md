Platform and deployment misconfigurations in a **React (frontend) and Node.js (backend)** stack occur when the underlying
servers, cloud environments, frameworks, or build pipelines are set up insecurely. While developers often focus heavily on
writing secure code, weaknesses in environment setup can expose the application to serious risks.

---

### Common Types of Misconfigurations in React & Node Stacks

#### 1. Information Disclosure via Environment Variables (`.env`)

- **The Issue:** Node.js applications frequently rely on `.env` files to store secrets, API keys, and database connection
  strings. In a React/Node setup, developers sometimes accidentally prefix variables with constants (like `REACT_APP_` or
  public flags) that cause bundlers (like Vite or Webpack) to bake secrets directly into the client-side JavaScript bundle.
- **The Risk:** Anyone can open the browser's developer tools, inspect the bundled JavaScript files, and extract sensitive
  API keys or internal service credentials hardcoded into the frontend.

#### 2. Insecure CORS (Cross-Origin Resource Sharing) Policies

- **The Issue:** Node.js backends (often built with Express) require explicit CORS configuration to determine which frontend
  domains can communicate with them. A common misconfiguration is setting the CORS header to wildcard values
  (`Access-Control-Allow-Origin: *`) or improperly handling credentials alongside wildcard origins.
- **The Risk:** An external, malicious website can make authenticated requests on behalf of a logged-in user to your Node.js
  backend, potentially reading or modifying sensitive data.

#### 3. Default Server Settings and Missing Security Headers

- **The Issue:** Node.js frameworks (like Express) do not enforce secure HTTP headers by default. If developers fail to use
  middleware like `helmet` or misconfigure reverse proxies (such as Nginx or Apache), critical headers may be missing.
- **The Risk:**
- Missing **Content Security Policy (CSP)** headers leave the app vulnerable to Cross-Site Scripting (XSS).
- Missing **Strict-Transport-Security (HSTS)** or insecure cookie flags (`HttpOnly`, `Secure`, `SameSite`) can expose session
  tokens to interception or theft via cross-site scripting.

#### 4. Unprotected API Endpoints and Directory Listing

- **The Issue:** Leaving debugging tools, server status endpoints, or directory listing enabled on the Node.js server or the
  web server hosting the static React build.
- **The Risk:** Attackers can map out the server's internal file structure, discover hidden administrative routes, or access
  unauthenticated monitoring endpoints that reveal system metadata.

#### 5. Outdated Dependencies and Framework Mismanagement

- **The Issue:** Failing to patch underlying packages or mismanaging server-side rendering (SSR) frameworks (such as Next.js
  or custom React server setups) can expose applications to severe flaws, such as deserialization issues or remote code
  execution risks.

---

### Best Practices for Hardening the Stack

- **Strict Environment Separation:** Keep backend secrets strictly on the server. Never use public prefixes for sensitive
  credentials meant only for the Node.js environment.
- **Secure CORS Configuration:** Explicitly define trusted frontend origins in your Node.js backend rather than using
  universal wildcards.
- **Harden HTTP Headers:** Implement security header middleware (e.g., Helmet for Express) and configure a robust Content
  Security Policy (CSP).
- **Manage Dependencies Regularly:** Run automated checks (`npm audit` or tools like Snyk) to catch vulnerable packages early
  in your CI/CD pipeline.
