In a React and Node.js stack, **Access Control** determines _who_ is allowed to access specific UI views, execute API
actions, or view/modify underlying data.

While **Authentication** verifies _who a user is_, **Access Control** enforces _what they can do_. Failures in access control
consistently rank among top web application security risks (OWASP Top 10).

---

### Core Access Control Vulnerabilities

#### 1. Insecure Direct Object References (IDOR / BOLA)

This occurs when an application exposes a database key or resource ID in the URL or request body without verifying if the
authenticated user owns that specific resource.

- **The Vulnerability:** A user logged in as `User A` requests `GET /api/documents/1001`. They change the URL to
  `GET /api/documents/1002` (belonging to `User B`).
- **The Cause:** The Node.js route authenticates `User A` but fails to check if `1002` belongs to `User A` before returning
  the document.

#### 2. Client-Side Access Control Reliance (UI Security Bypass)

A common mistake in React apps is assuming that hiding a UI component or route prevents access to the underlying feature.

- **The Vulnerability:** React hides the `<AdminPanel/>` tab or blocks the `/admin` route for standard users using
  client-side checks (`if (user.role !== 'admin')`).
- **The Attack:** An attacker inspects React props, modifies local storage/state variables, or accesses raw API endpoints
  directly (`POST /api/admin/delete-user`).
- **Rule:** Client-side routing in React is purely for **User Experience (UX)**. Real security enforcement must happen on the
  Node.js backend.

#### 3. Broken Function-Level Access Control (Vertical Privilege Escalation)

Occurs when administrative endpoints fail to verify role permissions on the backend.

- **The Cause:** A regular user discovers an endpoint intended for superusers or admins (e.g., `POST /api/users/promote`) and
  calls it directly via Postman or `fetch()`. The Node.js controller checks `req.user` exists (authenticated), but fails to
  verify `req.user.role === 'admin'`.

#### 4. Missing Ownership Checks (Horizontal Privilege Escalation)

Users with identical roles can view or modify each other's private data.

- **Example:** `User A` (Role: Customer) updates their user profile via `PUT /api/profiles/50`. If Node.js accepts
  `PUT /api/profiles/51` without ensuring that user ID `51` matches the authenticated `req.user.id`, `User A` can overwrite
  `User B`'s profile.

---

### Best Practices & Fixes

```
┌─────────────────────────────────────────────────────────────┐
│                      Client (React)                         │
│  - Hides UI elements (UX only)                              │
│  - Sends Auth Headers (JWT / Cookie)                        │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTP Request + Token
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                     Backend (Node.js)                       │
│  1. Authentication Middleware -> (Identify User)            │
│  2. Authorization Middleware  -> (Check Role/Permissions)   │
│  3. Controller/DB Query       -> (Verify Resource Ownership)│
└─────────────────────────────────────────────────────────────┘

```

#### 1. Enforce Server-Side Ownership Checks

Always query data using both the resource ID **and** the authenticated user ID from the session/token:

```javascript
// ❌ VULNERABLE Node.js Controller (IDOR)
app.get("/api/invoices/:id", authenticateToken, async (req, res) => {
  const invoice = await Invoice.findById(req.params.id);
  res.json(invoice);
});

// ✅ SECURE Node.js Controller
app.get("/api/invoices/:id", authenticateToken, async (req, res) => {
  const invoice = await Invoice.findOne({
    _id: req.params.id,
    ownerId: req.user.id, // Enforces ownership at DB layer
  });

  if (!invoice) {
    return res.status(404).json({ error: "Invoice not found or access denied" });
  }
  res.json(invoice);
});
```

#### 2. Implement Role-Based Access Control (RBAC) Middleware

Create centralized, reusable authorization middleware in Node.js to enforce permissions before request handlers run:

```javascript
// Node.js RBAC Middleware
const authorize = (...allowedRoles) => {
  return (req, res, next) => {
    if (!req.user || !allowedRoles.includes(req.user.role)) {
      return res.status(403).json({ error: "Forbidden: Insufficient permissions" });
    }
    next();
  };
};

// Apply to sensitive admin routes
app.delete("/api/users/:id", authenticateToken, authorize("admin"), deleteUserHandler);
```

#### 3. Secure React Routes (UX Only)

Use custom React route wrappers to redirect unauthorized users, while ensuring all sensitive API calls remain strictly
protected on Node.js:

```jsx
// React Protected Route Component
const ProtectedRoute = ({ allowedRoles, children }) => {
  const { user } = useAuth();

  if (!user) return <Navigate to="/login" replace />;
  if (!allowedRoles.includes(user.role)) return <Navigate to="/unauthorized" replace />;

  return children;
};
```
