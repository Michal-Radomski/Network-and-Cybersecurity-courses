Cross-Site Scripting (XSS) is a severe web security vulnerability that occurs when an application includes untrusted user
data in a web page without proper validation or escaping. This allows attackers to inject malicious scripts (usually
JavaScript) into legitimate website interfaces, which then execute directly inside the browsers of unsuspecting users. [1, 2,
3, 4, 5] Unlike SQL injection, which targets backend databases, XSS directly targets the end-users of an application. [6, 7,
8]

---

## How It Works: The Main Types of XSS

Attackers leverage three primary variations of XSS to compromise user browsers: [9, 10]

## 1. Stored (Persistent) XSS [11]

The malicious script is permanently stored on the target server (e.g., in a database, comment field, or forum post). When
other users request the stored data, the server embeds the script into the HTML page, and the script executes in their
browsers. [12, 13, 14, 15, 16]

- Example: An attacker posts a comment containing <script>stealCookies()</script>. Every user who views that comment section
  executes the script. [17, 18]

## 2. Reflected (Non-Persistent) XSS

The malicious script is part of an HTTP request (typically a URL parameter or form submission) and is immediately "reflected"
back by the server into the response page without being stored. [19, 20, 21, 22, 23]

- Example: An attacker crafts a link: https://example.com<script>attack()</script>. When a victim clicks this link, the
  backend reflects the script into the search results page, triggering execution. [24, 25, 26, 27]

## 3. DOM-Based XSS [28]

The vulnerability exists entirely on the client side (frontend). The application's JavaScript processes data from an
untrusted source (like window.location.search) and unsafely outputs it into the document object model (DOM), bypassing
backend checks entirely. [29, 30, 31, 32, 33]

- Example: Client-side JavaScript takes a URL hash and writes it directly to the page using an unsafe method:
  document.write(location.hash);. [34, 35, 36, 37]

---

## Potential Impact of a Successful XSS Attack

Because the injected script executes within the context of the victim's browser session, the attacker can perform any action
the user can: [38, 39, 40]

- Session Hijacking: Stealing sensitive session tokens or authorization cookies stored in the browser to log into the user's
  account.
- Data Theft: Scraping sensitive information displayed on the page, such as credit card details, personal profiles, or
  private messages.
- Phishing & Defacement: Arbitrarily modifying the page content (DOM) to display fake login forms that steal user
  credentials.
- Keylogging: Installing scripts that capture the user's keystrokes while they interact with the page. [41, 42, 43, 44, 45]

---

## Conceptual Examples: Vulnerable vs. Secure## Unsafe Implementation

If a web application prints user input directly into the HTML structure, it is vulnerable: [46]

<!-- If input is: <script>alert(1)</script> -->
<div>
  Welcome back, <?php echo $_GET['user']; ?>
</div>

The browser cannot distinguish between the developer's legitimate layout code and the attacker's injected code, so it runs
the script. [47, 48, 49]

## Safe Implementation

To fix this, the application must transform special characters into harmless textual representations (HTML Entities) so the
browser treats the input strictly as plain data: [50, 51, 52, 53]

<!-- Special characters are safely escaped: &lt;script&gt;alert(1)&lt;/script&gt; -->
<div>
  Welcome back, &lt;script&gt;alert(1)&lt;/script&gt;
</div>

## The browser will safely print the literal text on the screen without executing it. [54]

## Prevention Strategies

- Context-Aware Output Encoding: Convert characters like <, >, &, ", and ' into their corresponding HTML entities before
  rendering them in HTML body, attributes, JavaScript variables, or CSS styles. [55, 56, 57, 58, 59]
- Content Security Policy (CSP): Implement an HTTP header (Content-Security-Policy) that specifies exactly which domains the
  browser is allowed to load executable scripts from. A strong CSP can block inline scripts from running entirely. [60, 61,
  62, 63, 64]
- Use Modern Frameworks: Frameworks like React safely escape variables rendered in JSX by default (e.g., {userInput}),
  fundamentally mitigating most basic XSS risks unless you bypass protection using unsafe overrides like
  dangerouslySetInnerHTML. [65, 66, 67, 68]
- HttpOnly Cookies: Set the HttpOnly flag on sensitive authentication cookies. This ensures that client-side JavaScript
  cannot access the cookies, completely neutralizing session theft via XSS. [69, 70, 71, 72, 73]
