## Understanding Weak Auth Tokens and IDOR

Continuing our look at API vulnerabilities, two of the most critical security flaws involve how applications handle user
identification (**Weak Auth Tokens**) and resource permissions (**IDOR**).

---

## 1. Weak Auth Tokens

An **authentication token** acts as a digital key proving a user's identity after they log in. **Weak auth tokens** occur
when these keys are poorly generated, improperly signed, or easily manipulated.

- **Common Issues:**
- **Predictable Generation:** Using weak random number generators or sequential IDs to create tokens, allowing attackers to
  guess valid tokens for other users.
- **Weak Cryptography:** Using broken hashing algorithms or weak, easily guessable secret keys to sign tokens (such as JSON
  Web Tokens or JWTs).
- **Missing Expiration:** Tokens that never expire mean an attacker who steals a token has permanent access.

- **How to Fix It:**
- Use cryptographically secure random number generators for session tokens.
- For JWTs, use strong signature algorithms (like RS256 or secure HS256) backed by a long, randomly generated secret key.
- Implement short token lifetimes paired with secure refresh token rotation.

---

## 2. IDOR (Insecure Direct Object Reference)

**IDOR** (also known as Broken Object Level Authorization, or BOLA) happens when an application exposes a reference to an
internal database object—such as a user ID, file name, or account number—directly in the URL or request parameters, **without
checking if the current user is authorized to access it**.

- **How it Works:**
- A user logs in and requests their profile data via: `GET /api/users/105`
- If the user changes `105` to `106` in the URL and the server returns user `106`'s private data without checking
  permissions, an **IDOR** vulnerability exists.

- **How to Fix It:**
- **Implement Authorization Checks:** Never rely on the client to enforce who can see what. Every time a request comes in for
  a specific resource, the server must verify: _"Does the currently logged-in user have permission to access resource X?"_
- **Use Indirect References:** Instead of exposing sequential database IDs (like `101`, `102`), use unpredictable identifiers
  like UUIDs (`123e4567-e89b-12d3-a456-426614174000`). While UUIDs don't replace authorization checks, they prevent easy
  enumeration.
