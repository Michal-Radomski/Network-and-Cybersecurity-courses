## Is an API with Sessions RESTful?

Strictly speaking, **no**. An API that relies on server-side sessions is technically **not fully RESTful** because one of
REST's core architectural constraints is **statelessness**.

---

### The Conflict: Statelessness vs. Sessions

- **REST (Stateless):** The server must not store any state about the client session. Every single request from the client
  must contain all the information necessary for the server to understand and fulfill it (such as a token or API key).
- **Sessions (Stateful):** When a user logs in, the server creates a "session" and stores that data in its memory or a
  database. When subsequent requests come in with a session cookie, the server has to look up that session data to remember
  who the user is. Because the server is keeping track of the client's state, it breaks the strict definition of REST.

---

### Real-World Practice vs. Theory

While server-side sessions break the strict definition of REST, the software industry often bends the rules:

- **"REST-like" or HTTP APIs:** Many web applications use sessions and cookies for authentication because they are secure and
  easy to implement for browser-based apps. Developers often call these APIs "REST APIs" casually, even though purists would
  classify them simply as HTTP APIs.
- **True REST Authentication:** To keep a REST API truly stateless, developers usually use **Tokens** (like JSON Web Tokens
  or JWTs). Instead of looking up a session on the server, the client sends a signed token with every request, and the server
  simply verifies the math behind the token without storing any session data.
