## Understanding Sensitive Data in GET Requests

In web security, passing sensitive information (such as passwords, tokens, or personal data) through URL parameters in a
**GET request** is a well-known risk. It is formally tracked as **CWE-598** (_Use of GET Request Method With Sensitive Query
Strings_).

---

### Why GET Requests Are Insecure for Sensitive Data

When data is sent via a GET request, it becomes part of the URL string (e.g., `?username=...&password=...`). This creates
several security vulnerabilities because URLs are treated differently than request bodies:

- **Browser History & Auto-Complete:** Browsers automatically save URLs in history and auto-complete caches, meaning anyone
  sharing or using that device can see the credentials.
- **Web Server Logs:** Web servers, firewalls, and analytics tools routinely log full incoming URLs. This causes sensitive
  plaintext credentials to be permanently saved in log files, which might be accessible to many system administrators or
  prone to breaches.
- **HTTP Referer Headers:** If a user clicks an external link from that page, the browser often sends the entire
  URL—including query parameters—to the external site via the `Referer` header.
- **Proxies and Intermediaries:** Content Delivery Networks (CDNs) and corporate proxies cache URLs to improve performance,
  exposing the sensitive query parameters to third-party infrastructure.

---

### How to Remediate the Vulnerability

To protect sensitive data from exposure:

1. **Use `POST` or `PUT` Methods:** These methods send data inside the request **body** rather than the URL string.
2. **Enforce HTTPS:** Encrypt all web traffic in transit so that even when data is in the request body, it cannot be
   intercepted.
3. **Token-Based Authentication:** For API authentication, use authorization headers (like `Authorization: Bearer <token>`)
   instead of passing secrets in query parameters.
