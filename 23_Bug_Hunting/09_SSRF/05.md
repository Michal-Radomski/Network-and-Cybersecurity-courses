**Blind Server-Side Request Forgery (Blind SSRF)** is a web security vulnerability that occurs when a web application makes
an HTTP request to a backend server based on user-supplied data, but **does not return the response** from that request to
the user's browser.

Unlike standard SSRF, where the application displays the fetched data back to the attacker, a "blind" vulnerability hides the
output, making it harder to detect and exploit directly.

---

### How Blind SSRF Works

1. **The Request:** An application feature (like a webhook, link preview generator, or file downloader) accepts a URL from a
   user and tells its internal server to fetch it.
2. **The Execution:** The server makes the request to the target URL (which could be an internal system, an external API, or
   a local service).
3. **The Silence:** The server receives the response from the target, but instead of showing it on the webpage, it discards
   it or logs it internally. The user only sees a generic success or error message.

---

### Potential Impact

Because the application can be tricked into interacting with internal or external networks, attackers look for ways to infer
whether the request succeeded:

- **Out-of-Band (OAST) Detection:** Attackers use external servers they control to see if the vulnerable application pings
  them back.
- **Internal Network Scanning:** Even without seeing the response body, an attacker can sometimes measure response times or
  error codes to map out internal infrastructure that is normally hidden behind a firewall.
- **Triggering Actions:** If an internal API performs state-changing actions (like deleting data or triggering a build) via a
  simple GET or POST request, a blind SSRF can force the server to execute those actions unintentionally.

---

### Prevention and Defense

Securing applications against blind SSRF involves strict controls on how a server handles outbound requests:

- **URL Whitelisting:** Allow only specific, trusted domains or IP addresses for outbound requests.
- **Disable Dangerous Protocols:** Restrict the application to use only standard protocols like `https://` and block internal
  schemes like `file://`, `gopher://`, or `dict://`.
- **Network Segmentation:** Ensure that the servers making outbound requests are isolated from sensitive internal networks
  and databases.
