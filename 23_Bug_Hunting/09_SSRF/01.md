**Server-Side Request Forgery (SSRF)** is a web security vulnerability that allows an attacker to manipulate a vulnerable
server into making unauthorized HTTP requests on their behalf.

Because these requests originate from the server itself—which usually sits securely behind a firewall—the server often has
trusted access to internal networks, private databases, and cloud metadata services that are completely hidden from the
public internet.

---

### How an SSRF Attack Works

1. **Vulnerable Feature:** A web application includes features that fetch data from external URLs, such as link previews,
   image downloaders, document converters, or webhook integrations.
2. **Malicious Input:** Instead of providing a normal URL (e.g.,
   `[https://example.com/image.png](https://example.com/image.png)`), an attacker inputs a specially crafted internal
   address, such as `http://localhost/admin` or a cloud metadata address
   (`[http://169.254.169.254/](http://169.254.169.254/)`).
3. **Server Execution:** The server blindly processes the user input and makes a network request to that internal target.
4. **Data Leakage:** If the application returns the response back to the user (Standard SSRF), the attacker gains
   unauthorized view of internal data, configuration files, or administrative panels.

---

### Common Targets of SSRF

- **Internal Services:** Interacting with backend systems, databases, or microservices that lack separate authentication
  because they are assumed to be safe inside the corporate network.
- **Cloud Metadata Endpoints:** Many cloud providers (like AWS, Google Cloud, or Azure) use specific, local IP addresses
  (e.g., `169.254.169.254`) to supply server instances with temporary configuration data and administrative credentials. SSRF
  can expose these secrets.
- **Local Files:** Using schemes like `file:///etc/passwd` to read sensitive system files directly from the server's local
  file system.

---

### Types of SSRF

- **Standard (In-band) SSRF:** The application reflects the results of the server's request back to the user, allowing the
  attacker to immediately see the output.
- **Blind SSRF:** The server makes the requested internal call, but does not return the response to the user interface.
  Attackers detect success by monitoring external indicators like network timing differences or out-of-band DNS/HTTP pings to
  servers they control.

---

### Prevention and Mitigation

- **Use Allow-lists:** Strictly validate and restrict user-supplied URLs against a pre-approved list of trusted domains and
  protocols (e.g., permitting only `https` and blocking local/private IP ranges).
- **Disable Unused URL Schemes:** Turn off dangerous protocols like `file://`, `gopher://`, or `dict://` if the application
  only needs standard web traffic.
- **Isolate Network Architecture:** Ensure that web servers handling public traffic have restricted outbound network access
  and cannot directly communicate with sensitive internal infrastructure or cloud metadata services unless strictly required.
- **Disable Automatic Redirects:** Prevent the application from blindly following HTTP redirect chains, which attackers often
  use to bypass initial URL filters.
