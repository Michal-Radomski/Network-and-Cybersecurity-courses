**Open Redirect Vulnerability** (also known as Unvalidated Redirects and Forwards) is a web security flaw that occurs when an
application takes user-supplied input—usually a URL parameter—and redirects the user to that destination without properly
validating or sanitizing it.

Because users inherently trust links coming from legitimate domains, attackers can exploit this flaw to trick people into
visiting malicious external websites.

---

### How Open Redirect Works

1. **The Crafting:** An attacker creates a link to a trusted website that includes a redirection parameter pointing to a
   malicious site.

- _Example:_
  `[https://trusted-website.com/login?redirect=https://malicious-phishing-site.com](https://trusted-website.com/login?redirect=https://malicious-phishing-site.com)`

2. **The Click:** A user sees the trusted domain (`trusted-website.com`) at the beginning of the link, assumes it is safe,
   and clicks it.
3. **The Redirection:** The web application authenticates or processes the request, reads the `redirect` parameter, and
   automatically sends the user's browser to `[https://malicious-phishing-site.com](https://malicious-phishing-site.com)`.

---

### Potential Impact

While an open redirect might look harmless at first glance, it is frequently used as a stepping stone for larger attacks:

- **Phishing Campaigns:** Attackers use the trusted domain to bypass basic user suspicion, making phishing emails or social
  engineering attempts look completely authentic.
- **Credential Theft:** Victims may be redirected to a fake login page that mimics the original site to steal usernames,
  passwords, or session tokens.
- **Malware Distribution:** Users can be steered toward compromised pages designed to download malicious payloads onto their
  devices.

---

### Prevention and Defense

Securing an application against open redirects involves strict control over how navigation and redirection are handled:

- **Avoid User-Controlled Input:** Whenever possible, avoid using dynamic parameters to determine where a user should go
  after an action.
- **Use Relative Paths:** Restrict redirects to local, relative paths (e.g., `/dashboard`) rather than allowing full external
  URLs.
- **Implement Whitelists:** If external redirection is strictly necessary, maintain a strict whitelist of approved domains
  and check user input against it before executing the redirect.
