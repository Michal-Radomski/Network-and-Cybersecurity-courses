This URL is the intended solution for PortSwigger's “Reflected XSS protected by CSP, with CSP bypass” lab. P PortSwigger

Let's break it down piece by piece.

1. The search parameter search=%3Cscript%3Ealert%281%29%3C%2Fscript%3E

That is URL-encoded:

<script>alert(1)</script>

The browser/server decodes it, so the application reflects:

<script>alert(1)</script>

This is the reflected XSS part.

Normally, however, the lab's CSP prevents this inline script from running.

2. The token parameter

The interesting part is:

token=;script-src-elem%20%27unsafe-inline%27

After URL decoding:

token=;script-src-elem 'unsafe-inline'

The important character is the semicolon ;.

CSP directives are separated by semicolons. The lab unfortunately places the user-controlled token value inside its
Content-Security-Policy header. P PortSwigger

Conceptually, the server ends up generating something like:

Content-Security-Policy: default-src 'self'; object-src 'none'; script-src 'self'; style-src 'self'; report-uri
/csp-report?token=; script-src-elem 'unsafe-inline'

So you've effectively injected another CSP directive.

3. What does script-src-elem do?

This is the clever part of the lab.

The original policy contains:

script-src 'self'

which prevents arbitrary inline <script> elements.

But you're adding:

script-src-elem 'unsafe-inline'

script-src-elem specifically controls script elements, such as:

<script>alert(1)</script>

In Chrome, this more-specific directive can override the relevant script-src restriction for script elements. PortSwigger
specifically designed this lab around that behavior. P PortSwigger +1

And:

'unsafe-inline'

means that inline JavaScript is allowed.

So the browser effectively goes from:

script-src 'self' ↓ inline <script> blocked

to:

script-src-elem 'unsafe-inline' ↓ inline <script> allowed

4. Putting the two attacks together

You have two separate pieces:

XSS payload:

<script>alert(1)</script>

CSP bypass:

;script-src-elem 'unsafe-inline'

The complete URL combines them:

https://YOUR-LAB-ID.web-security-academy.net/?search=%3Cscript%3Ealert%281%29%3C%2Fscript%3E&token=;script-src-elem%20%27unsafe-inline%27

So the logic is:

          ↓                   ↓

          ↓                   ↓

<script>alert(1)</script>   ;script-src-elem
