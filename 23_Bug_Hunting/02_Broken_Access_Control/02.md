**Insecure Direct Object Reference (IDOR)** is a specific type of **Access Control vulnerability** (specifically, a form of
horizontal privilege escalation) that occurs when an application exposes a direct reference to an internal implementation
object—such as a database key, filename, or user ID—without proper authorization checks.

### How IDOR Works

1. **The Direct Reference:** When you use a web application, it often needs to fetch specific data from a database. To do
   this, it might use parameters in the URL or request body, like:

- `[https://example.com/account?id=1001](https://example.com/account?id=1001)`
- `[https://example.com/download?file=invoice_502.pdf](https://example.com/download?file=invoice_502.pdf)`

2. **The Flaw:** If the application trusts the user input blindly and fails to ask, _"Is the person currently logged in
   actually allowed to view ID 1001 or file 502?"_, an IDOR vulnerability exists.
3. **The Exploitation:** An attacker (or tester) can simply change that parameter to another value (e.g., changing `id=1001`
   to `id=1002` or `1003`) to view, modify, or delete data belonging to other users.

---

### Real-World Example

Imagine an online shopping platform where your order confirmation page shows your receipt via this URL:
`[https://shop.com/receipt?order_id=4521](https://shop.com/receipt?order_id=4521)`

If you change `4521` to `4520` in your browser's address bar and the page instantly loads another customer's private receipt
(showing their name, delivery address, and partial payment info), that is a classic IDOR vulnerability.

### Why Does It Happen?

- **Lack of Authorization Checks:** Developers often rely solely on session authentication ("Are you logged in?") rather than
  authorization checks ("Are you allowed to access _this specific_ record?").
- **Predictable Identifiers:** Using sequential numbers (1, 2, 3...) makes it very easy to guess and iterate through other
  users' data compared to using randomized tokens like UUIDs.
