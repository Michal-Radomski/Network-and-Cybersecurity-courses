## The Danger of Verbose Errors in Node.js

In Node.js applications—especially those built using frameworks like Express—default error handlers frequently dump raw stack
traces, file paths, and dependency versions straight to the client. If an error occurs in production, this information leaks
your internal directory structure and codebase logic directly to visitors.

## Vulnerable vs. Secure Error Handling

- **Vulnerable Approach:** Sending `err.stack` or raw database error objects directly in the HTTP response.
- **Secure Approach:** Logging the error securely on the server backend while returning a generic, friendly message to the
  user.

### Example Code

```javascript
// Vulnerable Middleware (Leaks information)
app.use((err, req, res, next) => {
  res.status(500).send(err.stack); // Exposes internal file paths and code logic
});

// Secure Middleware (Protects sensitive data)
app.use((err, req, res, next) => {
  console.error(err); // Log the full stack trace privately on the server
  res.status(500).json({ error: "Something went wrong. Please try again later." });
});
```

## Best Practices to Prevent Leaks in Node.js

- **Use Environment Checks:** Wrap detailed error responses in a condition that checks if
  `process.env.NODE_ENV === 'development'`.
- **Hide Server Headers:** Use security packages to automatically remove revealing response headers (like
  `X-Powered-By: Express`).
- **Sanitize API Responses:** Ensure controllers don't accidentally return entire database user objects containing password
  hashes or internal tracking IDs.
- **Regularly Audit Dependencies:** Keep your `npm` packages updated to avoid known information disclosure vulnerabilities in
  third-party code.
