**CSRF** (which stands for **Cross-Site Request Forgery**, and is often pronounced "sea-surf") is a web security
vulnerability that tricks a logged-in user into performing unwanted actions on a web application without their knowledge or
consent.

Here is a breakdown of how CSRF works, a conceptual example, and how developers prevent it.

---

## How CSRF Works

To understand CSRF, it helps to know how web applications recognize you. When you log into a website (like your bank or
email), the server gives your browser a session cookie. Whenever you click a button or submit a form on that site, your
browser automatically attaches that cookie so the server knows it's really you.

- **The Trick:** A CSRF attack exploits this automatic behavior. If you visit a malicious website while still logged into a
  vulnerable site (like your bank), the malicious site can secretly send a request to your bank.
- **The Mechanism:** Your browser, trusting that you intended to make the request, automatically attaches your valid session
  cookies. The bank's server sees valid credentials and executes the action (such as transferring money or changing your
  password), thinking _you_ requested it.

---

## Conceptual Example

Imagine a vulnerable social media site where users can change their email address using a simple link:
`[https://example.com/update-email?email=newemail@hacker.com](https://example.com/update-email?email=newemail@hacker.com)`

1. An attacker sets up a malicious website or embeds an invisible image/form on a forum page that automatically loads that
   URL.
2. If you visit that page while logged into `example.com`, your browser automatically sends the request with your active
   session.
3. The server updates your email to the attacker's email address, locking you out of your account—all without you ever
   clicking that link directly.

---

## Prevention and Remediation

Web developers use several standard defenses to protect applications from CSRF attacks:

- **Anti-CSRF Tokens (Synchronizer Token Pattern):** The server generates a unique, secret, and unpredictable random token
  for each user session. When the user submits a form, the application must include this token. Because an external malicious
  site cannot read this secret token, it cannot forge a valid request.
- **SameSite Cookie Attribute:** Developers can set the `SameSite` attribute on cookies to `Strict` or `Lax`. This tells the
  browser not to send cookies along with cross-site requests, effectively blocking the core mechanism of CSRF.
- **Re-Authentication:** For sensitive actions (like changing a password or transferring funds), applications often require
  the user to re-enter their current password, ensuring a human is actually performing the action.
