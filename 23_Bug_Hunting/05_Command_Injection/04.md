**Blind Command Injection** is a type of command injection vulnerability where the application executes the system command
supplied by the user, but it **does not return the output** (the results, data, or error messages) directly on the screen or
in the application's response.

In a standard command injection scenario, an attacker might see the text output of a command (like the result of a directory
listing or a network ping) displayed back to them. In a _blind_ scenario, the application simply returns a generic response,
such as a standard "Thank you" page or a generic error message, regardless of whether the command succeeded or failed.

---

### How Blind Command Injection is Tested or Identified

Because the application doesn't show the output directly, security professionals and developers testing for this
vulnerability look for indirect indicators that a command was executed:

1. **Time Delays (Time-Based Detection):** If an application executes a command that tells the operating system to pause or
   sleep for a specific number of seconds before responding, a tester can measure how long the server takes to reply. If the
   response is delayed by that exact number of seconds, it indicates that the system processed and executed the injected
   command.
2. **Out-of-Band (OOB) Communication:** An injection can be structured to force the server to make a network request to an
   external server or domain controlled by the tester (such as a DNS lookup or an HTTP request). If the external server
   receives that request, it proves that the system command was successfully executed behind the scenes.

---

### Why It Matters

Blind command injection carries the same severe risks as standard command injection (such as full server compromise or
unauthorized access). The only difference is _how_ the results are observed by someone testing or exploiting the system.

### Prevention

The prevention methods for blind command injection are identical to standard command injection:

- **Avoid shell execution** functions whenever possible.
- **Use safe execution methods** like `execFile` or `spawn` with argument arrays.
- **Implement strict input validation** and allowlisting to ensure users can only input expected, safe data.
