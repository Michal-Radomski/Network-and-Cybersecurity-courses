OAuth 2.0 is an industry-standard authorization protocol that allows third-party applications to obtain limited access to a
user's resources without exposing their password.

The most common and secure flow used today—especially for web and mobile applications—is the **Authorization Code Flow with
Proof Key for Code Exchange (PKCE)**.

---

### Key Actors in the Flow

- **Resource Owner:** The user who owns the data and grants access.
- **Client:** The application wanting to access the user's data (e.g., a mobile app or website).
- **Authorization Server:** The server that authenticates the user and issues access tokens (e.g., Google, GitHub).
- **Resource Server:** The server hosting the protected user data (e.g., Google Drive API).

---

### Step-by-Step Flow

1. **Authorization Request:** The client application redirects the user's browser to the Authorization Server. The request
   includes the client ID, requested permissions (scopes), redirect URI, and a code challenge (for PKCE security).
2. **User Authentication & Consent:** The user logs into the Authorization Server (if not already logged in) and sees a
   prompt asking if they want to grant the client application access to their account. If the user approves, the server
   generates an **Authorization Code**.
3. **Authorization Code Response:** The Authorization Server redirects the user back to the client application's specified
   redirect URI, attaching a temporary **Authorization Code** in the URL query parameters.
4. **Access Token Request:** The client application receives the authorization code and sends a direct, secure backend
   request to the Authorization Server. It includes the authorization code, client ID, and the code verifier (matching the
   PKCE challenge from Step 1).
5. **Access Token Response:** The Authorization Server validates the code and verifier. If everything is correct, it responds
   by issuing an **Access Token** (and optionally a Refresh Token).
6. **Access Protected Resources:** The client application can now use the Access Token in the header of API requests to the
   Resource Server to fetch the user's data on their behalf.

---

> **Note:** The Access Token has a limited lifespan for security. When it expires, the client can use a **Refresh Token** (if
> obtained) to request a new Access Token without requiring the user to log in again.
