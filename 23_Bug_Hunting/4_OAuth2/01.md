**OAuth 2.0** is an industry-standard authorization framework that allows applications to obtain limited access to a user's
resources on another service (such as Google, Facebook, or GitHub) without exposing the user's password.

Instead of handing over login credentials, a user grants an application a set of permissions (scopes), and the authorization
server issues an **access token**.

---

## Core Components of OAuth 2.0

- **Resource Owner:** The user who owns the data and grants access.
- **Client:** The third-party application requesting access to the user's data.
- **Authorization Server:** The server that authenticates the user and issues access tokens (e.g., Google's auth server).
- **Resource Server:** The API server hosting the protected user data.

---

## Common OAuth 2.0 Vulnerabilities

Because OAuth 2.0 is a flexible framework rather than a strict protocol, developers often misconfigure implementations,
introducing critical security flaws.

### 1. Redirect URI Manipulation (Open Redirection)

- **The Issue:** During the authorization flow, the server redirects the user back to the client application via a
  `redirect_uri` parameter. If the server performs weak validation (e.g., allowing wildcards, partial matches, or path
  traversal), an attacker can substitute a malicious URL.
- **The Impact:** The authorization code or access token is sent directly to the attacker's server instead of the legitimate
  application, leading to account takeover.

### 2. Missing or Flawed `state` Parameter (CSRF)

- **The Issue:** The `state` parameter is an opaque, unpredictable token used to maintain state between the request and the
  callback, protecting against Cross-Site Request Forgery. If it is omitted or improperly validated, attackers can trick a
  user into completing an OAuth flow bound to the attacker's account.
- **The Impact:** The victim's account gets linked to the attacker's external login provider, allowing the attacker to access
  or control the victim's data.

### 3. Insecure Implicit Grant Flow

- **The Issue:** The legacy Implicit Grant flow returns the access token directly in the URL fragment instead of using an
  authorization code exchanged via a secure back-channel.
- **The Impact:** Exposes the access token to browser history, server logs, or third-party scripts via Cross-Site Scripting
  (XSS) or Referer headers. _(Modern security standards strongly discourage the implicit flow, recommending the Authorization
  Code Flow with PKCE instead.)_

### 4. Insufficient Scope Validation

- **The Issue:** Applications sometimes request or accept broader permissions (scopes) than necessary. If an attacker
  compromises a low-privilege token, but the server fails to properly validate scopes, the token might grant access to
  high-privilege sensitive endpoints.

### 5. Token Leakage and Insecure Storage

- **The Issue:** Access tokens and refresh tokens act as digital keys. Storing them insecurely—such as in browser
  `localStorage` where they are vulnerable to XSS, or accidentally committing them to public source code repositories—allows
  persistent unauthorized access.

---

## Best Practices for Secure Implementations

- **Use the Authorization Code Flow with PKCE (Proof Key for Code Exchange):** This prevents authorization code interception
  attacks, making it ideal for web, mobile, and single-page applications.
- **Enforce Strict Redirect URI Matching:** Use exact string matching on the server side rather than regex or wildcard
  matching.
- **Always Implement the `state` Parameter:** Protect every flow with a unique, cryptographically secure random value to
  prevent CSRF.
