When designing a secure session cookie or session payload, you want to store only the minimum information necessary to
identify the user while keeping security and privacy in mind.

Here are the key elements that should be included or configured:

---

### 1. What to Store Inside the Session Data

- **User Identifier (ID):** A unique, randomized database ID or UUID representing the logged-in user. **Never** store
  sensitive data like passwords, password hashes, or Social Security numbers inside a session.
- **Role / Permissions (Optional):** Basic authorization flags or roles (e.g., `role: "user"` or `role: "admin"`) if needed
  for quick routing, though these can also be verified server-side on every request for higher security.
- **Session Expiration / Timestamp:** Metadata indicating when the session was created or when it expires, helping the server
  manage absolute timeouts.

---

### 2. Essential Cookie Security Flags (HTTP Headers)

If your application stores the session identifier directly in a cookie (rather than an in-memory token), the cookie **must**
be configured with these security attributes:

- **`HttpOnly`:** Prevents client-side JavaScript (like malicious XSS scripts) from reading or stealing the cookie.
- **`Secure`:** Ensures the browser only transmits the cookie over encrypted HTTPS connections.
- **`SameSite=Strict` or `SameSite=Lax`:** Protects against Cross-Site Request Forgery (CSRF) by controlling whether cookies
  are sent on cross-site requests.
- **`Path=/` and `Domain`:** Restricts the cookie to your application's specific domain and paths.

---

### 3. What to Avoid Storing

- **Personally Identifiable Information (PII):** Avoid storing plain-text email addresses, phone numbers, home addresses, or
  full names directly in the session or cookie.
- **Secrets or API Keys:** Never expose internal API keys, tokens for third-party services, or sensitive cryptographic keys
  on the client side.
