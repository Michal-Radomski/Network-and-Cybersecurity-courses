**Reflected XSS (Cross-Site Scripting)** is a web security vulnerability where malicious JavaScript is included in a request
and the server immediately reflects that input into the HTTP response without properly escaping or sanitizing it.

### How it works

1. A website accepts user-controlled input, such as a URL parameter.
2. The server places that input into the returned HTML.
3. An attacker creates a specially crafted URL containing JavaScript.
4. When a victim visits the URL, the browser interprets the reflected input as script and executes it in the context of the
   vulnerable website.

For example, a vulnerable application might effectively generate:

```
<p>Search results for: USER_INPUT</p>
```

If `USER_INPUT` is inserted without appropriate output encoding, HTML/JavaScript syntax supplied by the user could be
interpreted as executable code.

### Why it's called "reflected"

The malicious input **isn't permanently stored** on the server. Instead, it travels in the request and is **reflected
straight back** in the response.

This distinguishes it from:

- **Reflected XSS:** payload comes through a request and is immediately reflected.
- **Stored XSS:** malicious content is stored by the application and later served to other users.
- **DOM-based XSS:** the vulnerability occurs primarily in client-side JavaScript when it processes attacker-controlled data
  unsafely.

### Prevention

The main defense is **context-appropriate output encoding**—for example, HTML-encoding data before inserting it into HTML.
Applications should also avoid unsafe DOM APIs such as assigning untrusted data to `innerHTML`, validate inputs where
appropriate, and use a well-configured **Content Security Policy (CSP)** as an additional defense.
